About Fabric Lakehouse

This environment follows Microsoft's Medallion Architecture in Microsoft Fabric. Data progresses through Bronze (raw source data), Silver (validated and transformed business-ready datasets), and Gold (curated views optimized for reporting, analytics, and the data that powers Argus).

Each layer improves data quality, governance, and reusability while preserving full lineage back to the original source.

Aurora AI Offsite · June 2026
~150 people. 21 teams. One day to go from problem to working prototype. Team 20 built a single HTML file called Argus — a client-intelligence dashboard that unified Salesforce, Zendesk, Productboard and PostHog around a single account view. Three screens: Client health card, Ask Argus (AI chat), and Pre-call briefing. The prototype proved the idea was worth building properly. What you're looking at now is that build.
Aurora's commercial data is rich — but it lives in silos
Salesforce holds subscriptions and accounts. Zendesk holds support history. Productboard holds what clients are asking for. EOS holds how much they actually use the product. Nobody has all four in front of them at once.
Before Argus
✕Pre-call prep means opening SF, then ZD, then PB — each in a separate tab, mentally joining the picture yourself
✕Renewal risk is invisible until an account flags a concern or a manager pulls the report manually
✕Ad-hoc questions ("which Power & Renewables clients haven't renewed in 18 months?") require IT or a data analyst
✕The same client appears under three different names across SF, ZD and PB — no unified identity
With Argus
✓One account view: subscriptions, ARR, renewal date, open tickets, and platform usage in a single screen
✓At-risk renewals surface automatically — OVERDUE, AT_RISK and TO_WATCH flagged before they become urgent
✓CS and RPM answer their own data questions — no IT request, no waiting for a report
✓MDM layer resolves account identity across all sources — one canonical record per client
The bigger picture — Aurora data in plain English
The Argus App is phase one — a live dashboard giving CS and RPM a single view of account health, renewal risk, support activity and feature demand across Salesforce, Zendesk, Productboard and EOS. Phase two connects the same data to Claude Enterprise — so instead of clicking through the Argus App, a CS manager types "brief me on Shell before my 3pm call" and gets a live, synthesised answer pulled from Salesforce, Zendesk, Productboard and EOS in seconds. The data foundation being built now is what makes that possible — without it, Claude has nothing reliable to read from.

What Claude can do once this is live
Aurora staff ask plain-English questions in Claude. The MCP server queries our live Salesforce, Zendesk and Productboard data and returns a structured answer — no dashboard, no SQL, no waiting for a report.
— "Brief me on TotalEnergies before my 2pm call"
Claude returns: 12 active subscriptions · £850k ARR · renewal due March 2027 · 2 open Zendesk tickets (1 escalated) · Power & Renewables focus — aligns with the upcoming LNG feature release they've requested
— "Which accounts are renewing in the next 30 days with ARR over £200k?"
Claude returns a ranked list — Equinor overdue, Shell in 12 days, BP in 28 — with ARR, contract type and renewal owner for each
— "What features are Power & Renewables clients asking for most right now?"
Claude pulls the top-scored Productboard features for that segment — useful for pre-call prep or shaping a commercial conversation
Why this isn't live yet — three one-time IT tasks
1
Service principal for Fabric
IT creates an Azure AD identity that the server uses to authenticate to our Fabric data warehouse. Without this, no data can be read. It's the same mechanism Power BI uses today — we just need a separate one for Argus.
2
Azure App Service hosting
The Argus app and MCP server need to run at a permanent HTTPS URL — not on a laptop. IT provisions an App Service (small, low cost), adds M365 Easy Auth so Aurora staff sign in with their existing Microsoft account. Setup is roughly a half-day of IT time.
3
Claude Enterprise admin config
Once the server is live at its URL, an Aurora Claude admin registers it in the Claude Enterprise workspace settings. After that, every Aurora user can immediately ask Claude questions against live data — no individual setup required.
Once these three steps are done, it is self-service for every Aurora user — no further IT involvement for each person who uses it.

For IT — architecture note
Both Argus and the MCP server run on the same Node.js codebase and share the same API layer — a schema change in a Gold table is fixed once, not twice. Azure App Service (B1 tier) hosts both at separate subdomains. M365 Easy Auth gates access to Aurora-authenticated users. The MCP server exposes tools over HTTP; Claude Enterprise calls them on demand via the URL registered in the Anthropic admin console. No data is stored by Claude — every query hits Fabric live and returns only the rows needed.
